# Bend 2 xTranslator Importer: Fallout 4 design

Design revision: 0.5, 2026-11-06. This revision corrects only the platform scope; the recorded independent design reviews concern revision 0.4, which incorporated rounds 1 through 3. This is a proposed, testable implementation specification, not an implemented or certified importer. The complete intended product handles both inline and localized Fallout 4 plugins. Milestones below deliberately separate those capabilities; an inline-only prototype must never be advertised as completing the full product.

## 1. Product contract and non-negotiable properties

Build a command-line program, provisionally `bend-xt`, that applies selected xTranslator XML translations to a copy of one Fallout 4 ESP, ESM, or ESL plugin. The parser, XML adapter, matching, codecs, plugin rewriting, string-table handling, hashes, and compression algorithms are written in Bend 2. Ordinary OS effects remain runtime primitives, as Bend's existing file APIs already are. Do not substitute xEdit, Python, Rust, JavaScript, or an external converter for any production parsing or rewriting step.

The program is a conservative rewriter, not a plugin generator, merger, translation engine, load-order resolver, or replacement for Creation Kit. It changes only explicitly selected, supported text locations and the size/compression metadata necessarily enclosing them. Unknown records, fields, flags, order, and bytes are preserved when an operation is allowed, but may make an edit unsafe and therefore unsupported. Byte preservation alone does not preserve the meaning of stored file offsets after relocation. It does not compact FormIDs, reorder masters, create overrides, rename plugins, change localization/ESL/ESM flags, strip offset metadata, or repair malformed inputs.

Success means every selected XML entry has a documented result, every intended change is verified, and a new output bundle has been published without overwriting the inputs or any existing output. No silent partial success. Unsupported targeted content is a hard error unless the user explicitly excluded those entries before planning. Being able to copy an unknown field is not support for translating it.

The initial required runtime target is Linux native binaries on a tested Linux filesystem. WSL/WSL2 was added as a design assumption, not a user requirement; it is not a prerequisite for Linux-native use or an acceptance gate for the initial product. WSL support is a separate scope to consider if requested, and would require its own runtime, resource-limit, filesystem, and publication/durability validation. Native Windows remains a possible later runtime port; this correction does not declare Windows support unnecessary. Do not claim that storing files on a Windows-mounted filesystem has the same publication/durability semantics until those semantics pass tests. Output is a replacement copy with the **original plugin filename**, inside a new directory. It must not be installed as a second plugin alongside the original. The CLI never installs into the live game directory.

## 2. Evidence and pinned dependencies

Primary sources inspected:

- Bend 2 is now [bendlang/bend](https://github.com/bendlang/bend); the inspected commit is `266b02ee40a2ad0c42608db32c08c5c7b6a8f5ae`. Its [README](https://github.com/bendlang/bend/blob/266b02ee40a2ad0c42608db32c08c5c7b6a8f5ae/README.md) and [Base](https://github.com/bendlang/bend/blob/266b02ee40a2ad0c42608db32c08c5c7b6a8f5ae/bend2/base.bend) show `IO.args`, byte file reads/writes, U32 offsets, exclusive-create mode, and affine arrays. Current limitations include no U64/I64, no native Windows, a small standard library, and no general test framework. No stock `File.rename` or `fsync` was found in inspected Base. Pin a tested compiler commit rather than floating `main`.
- xTranslator reference revision is `9aa38d60860273401f8bb0dd1557c82a295c41b3` (public source identifies itself as 1.6.0). [TESVT_XMLFunc.pas](https://github.com/MGuffin/xTranslator/blob/9aa38d60860273401f8bb0dd1557c82a295c41b3/TESVT_XMLFunc.pas) defines its export dialect; [TESVT_typedef.pas](https://github.com/MGuffin/xTranslator/blob/9aa38d60860273401f8bb0dd1557c82a295c41b3/TESVT_typedef.pas) defines exported identity forms; [TESVT_espDefinition.pas](https://github.com/MGuffin/xTranslator/blob/9aa38d60860273401f8bb0dd1557c82a295c41b3/TESVT_espDefinition.pas) implements fields, indexes, and contextual cases. Later xTranslator binaries need their own captured fixtures, not an assumption of compatibility.
- [FO4 record definitions](https://github.com/MGuffin/xTranslator/blob/9aa38d60860273401f8bb0dd1557c82a295c41b3/Data/Fallout4/_recorddefs.txt) map XML lists to table kinds and distinguish contextual fields. [FO4 code pages](https://github.com/MGuffin/xTranslator/blob/9aa38d60860273401f8bb0dd1557c82a295c41b3/Data/Fallout4/codepage.txt) use `en=1252` and UTF-8 for many other languages. Therefore neither “all FO4 strings are CP1252” nor “every existing FO4 file is valid UTF-8” is a safe input assumption.
- [xEdit FO4 definitions](https://github.com/TES5Edit/TES5Edit/blob/9058a79437367c2cb1b757a9021ab443d743012d/Core/wbDefinitionsFO4.pas), inspected on `dev-4.1.5`, corroborate record-specific text types, including GMST's discriminator and PERK's union. They also expose TES4/OFST, WRLD/OFST, WRLD/CLSZ and offset-removal hooks; these are a warning against assuming all copied opaque metadata survives relocation. This importer does not imitate xEdit's removal behavior. [FO4 record framing](https://tes5edit.github.io/fopdoc/Fallout4/Records.html) describes 24-byte records, six-byte subrecord headers, and the compressed payload wrapper. These are implementation references, not an official Bethesda specification.
- [xTranslator string-table implementation](https://github.com/MGuffin/xTranslator/blob/9aa38d60860273401f8bb0dd1557c82a295c41b3/TESVT_StringsFunc.pas), [RFC 1950](https://www.rfc-editor.org/info/rfc1950/), and [RFC 1951](https://www.rfc-editor.org/info/rfc1951/) are the table and zlib/DEFLATE references.

Record source revisions and licenses in `sources.lock`. Implement from the format specifications; any copied or adapted source must retain its required notices and license obligations. These sources do not establish support for every FO4 variant or every third-party XML producer.

## 3. CLI and user-visible behavior

Proposed commands:

```
bend-xt capabilities --game fo4
bend-xt inspect --game fo4 --plugin Example.esp
bend-xt plan --game fo4 --plugin Example.esp --xml Example.xml \
  --plugin-encoding utf8 --source-language en --target-language ja \
  --report plan.json
bend-xt apply --game fo4 --plugin Example.esp --xml Example.xml \
  --plugin-encoding utf8 --source-language en --target-language ja \
  --out-dir ./Example-ja
bend-xt verify --bundle ./Example-ja
bend-xt verify --bundle ./Example-ja --provenance \
  --plugin Example.esp --xml Example.xml --game fo4 \
  --plugin-encoding utf8 --source-language en --target-language ja
```

The plan command is read-only except for an explicitly requested report file, which is created exclusively. Apply internally recomputes and validates the entire plan; it never trusts editable byte offsets in a saved report. A later `--expect-plan-digest` can require equality with a previous plan's canonical digest without using that report as authority.

`verify --bundle` performs **integrity-only verification**: it validates supported artifact structure and internal manifest consistency, not the claim that only authorized translations changed. `verify --bundle --provenance` additionally requires the original plugin, XML, all original source/target-baseline tables used by the import, and explicit import options; it recomputes the plan and compares original-to-output invariants. Its output names which verification level passed. Missing original inputs prevent a provenance pass and must never silently downgrade to integrity-only success. See section 9 for manifest trust and snapshot retention.

`--game fo4` is mandatory. Do not autodetect game solely from filename or HEDR version. Require a tested FO4 header/form-version profile; reject an unsupported version, and report the explicit version encountered. Extensions are accepted as containers only; the actual TES4 header controls localized/master/light behavior.

Explicit options are recorded in the report: encoding, XML dialect, newline policy, entry selection, status inclusion, source/target languages, supported field-profile version, resource limits, and any precise exception approvals. No general `--force`, source-only fuzzy matching, or “ignore all mismatches” switch.

Selection defaults: include completed entries (Partial absent) and locked translations (Partial=2); exclude Partial=1 entries as incomplete, showing their count. An explicit include-incomplete option adds those entries to the selected set and records that choice. Unknown statuses are invalid. An absent Dest is invalid; an empty Dest is distinct and requires `--allow-empty`, plus the field must permit emptiness. Never silently convert an empty translation to a space. Source=Dest remains a selected entry and is not automatically a no-op: a localized destination baseline may contain a different value which must be changed to Dest.

Exit statuses: 0 verified success/no-op; 2 invalid command/configuration; 3 malformed/unsupported input; 4 match or policy conflicts; 5 resource-limit failure; 6 IO/publication failure; 7 post-write verification failure. A failed apply must not leave a published-looking bundle. Report selected, excluded, changed, unchanged, already-applied, unsupported, unmatched, ambiguous, source-mismatched, and conflicting counts, each linked to XML entry locations. A zero-change plan prominently says so.

For localized plugins add explicit `--source-strings-dir`, `--source-table-encoding`, `--target-language`, and `--target-table-encoding`; either an existing `--target-strings-dir` or explicit `--untranslated source` supplies untranslated values. No archive lookup or heuristic directory search in the first release. The single-language bundle contract in section 8 is mandatory.

## 4. Architecture and Bend boundaries

Suggested modules:

- `core/bytes.bend`: checked cursor, little/big-endian reads, byte ranges, bounded chunks, checked arithmetic.
- `core/utf8.bend`, `core/cp1252.bend`: strict codecs with round-trip tests.
- `xml/tokenizer.bend`, `xml/xtranslator_v2.bend`: bounded XML lexer/parser and typed entries.
- `plugin/frame.bend`, `plugin/subrecords.bend`: format framing independent of game-specific field meanings.
- `compression/zlib.bend`, `compression/inflate.bend`, `compression/deflate_store.bend`, `compression/adler32.bend`.
- `games/profile.bend`, `games/fo4.bend`: versioned profile, field codec, contextual matcher, table mapping, empty-string rule, index semantics, text-token validator.
- `strings/table.bend`, `strings/allocate_id.bend`: table framing and localized output policy.
- `match/index.bend`, `match/resolve.bend`, `plan/validate.bend`: deterministic target selection and conflict collection.
- `write/record.bend`, `write/plugin.bend`, `verify/diff.bend`: minimal patching and independent invariants.
- `report/json.bend`, `hash/sha256.bend`, `cli/main.bend`, `host/io.bend`.
- `LAWS.bend`, `PROOF.bend`, `tests/`: selected proven properties and executable tests.

Use algebraic variants such as `InlineZString(encoding)`, `LocalizedId(tableKind)`, `Unsupported(reason)`, and `Conditional(predicate)`; never one undifferentiated “string field” type. Game adapters are explicit records of functions and data, not imagined traits or dynamic plugins unavailable in Bend. A new game supplies header/framing variations, text fields, codecs, flags, tables, and fixtures. Shared mechanics do not imply game support.

Model a parsed file as immutable record/group metadata plus original byte spans. The IO shell snapshots inputs into a private work directory, outside the publishable output tree, and computes Bend SHA-256 digests. Subsequent planning and writing use those snapshots, so a source file changing during an import cannot create a hybrid output. Snapshot acquisition checks the original handle's identity/size/metadata before and after copying and reports a change; the digest of the actual copied bytes is the definitive input identity. Do not claim an adversarial same-user writer cannot race metadata checks. User-owned files should not be edited concurrently. Snapshots remain available through full prepublication verification, are never automatically shipped in the bundle, and are removed when the run completes or fails. An explicit `--retain-input-snapshots DIR` may retain them separately in a new private directory; otherwise the user must keep the original inputs for a later provenance audit. Deleting scratch snapshots must never delete originals or published artifacts.

Use bounded 64 KiB IO chunks, affine buffers, and streaming passes. Keep only current decompressed record(s), structural indexes, and selected translations in memory. Avoid linked-list random access, repeated string concatenation, and copying full files. Bend `Array.get` returns the array along with the value; the implementation must thread ownership, not pretend arrays are freely shared. Record-level parallelism is optional after correctness/performance measurements, never parallel writes. Stable file order and allocation order make output deterministic.

All byte values are checked 0..255. File and format offsets are U32 with checked operations. Check `size <= end - position` before adding; do not wrap U32 and then compare. Use Nat or explicit high/low limbs only where required, not float offsets. Restrict every snapshot/output to below 4 GiB because the inspected native API uses U32 offsets. Initial defaults: 256 MiB plugin; 64 MiB XML; 32 MiB expanded record; 1 GiB cumulative expanded bytes per pass; group depth 64; XML depth 64; 200,000 XML entries; 1 MiB UTF-8 text per entry; 2 million records; 8 million subrecords. Limits are adjustable only within tested arithmetic/runtime ceilings. Profile and report the actual peak RSS, not theoretical byte-buffer size.

Localized-table budgets are separate and checked **before** count-sized allocation or processing: 200,000 directory entries per table and 600,000 across all source/target-baseline tables; 64 MiB per input table and 256 MiB aggregate input-table bytes; 1 MiB encoded bytes per referenced string including terminator (excluding the DL/IL length prefix); 512 MiB aggregate logical referenced string bytes, charging each directory entry even when it aliases another entry. Check declared counts, directory-byte multiplication, declared data lengths and actual file size before allocating the directory/index. Output preflight caps each output table at 128 MiB, all output tables at 384 MiB, and the complete output bundle's artifact bytes at 1 GiB. All are limits, not claims that those sizes are fast or memory-safe without the runtime gate.

Validation/decoding/encoding work is also metered: at most 1 GiB total table-byte visits across a plan/apply run, including repeated scans, codec work and verification; cached identical spans are charged once for decoding but every traversal still consumes its actual work budget. Provenance verification starts a new bounded run. Reject an operation before exceeding a counter; no wraparound or per-entry reset. Before allocating buffers or indexes, reserve from a 256 MiB live payload/index budget using conservative measured runtime representation costs, and enforce an independent 1 GiB process-memory ceiling on supported hosts. Gate A must validate that enforcement on the pinned runtime; nominal input byte counts are not enough for Bend's representation. Memory-limit termination may prevent a detailed report but must never permit unverified publication. Allocation-ID rescans and compressed-input passes have their own cumulative work budgets as well, not unlimited restarts.

The first engineering gate must compile and run actual Bend 2 programs for binary IO (including NUL), argv, exit codes, chunk ownership, SHA-256, and error handling on the pinned runtime. The design is not executable Bend syntax. No fake package names, unverified compiler flags, or promises of automatically proven end-to-end safety.

## 5. Plugin and compression framing

All ordinary plugin fields here are little-endian. A FO4 record header is 24 bytes: signature[4], payload size u32, flags u32, FormID u32, revision[4], form version u16, unknown[2]. Preserve header bytes except payload size and any explicitly allowed field. TES4 must be the first record and unique. Its localized bit is `0x80`; record compression bit is `0x00040000`. Treat other bits as contextual, not a universal enum.

GRUP headers are 24 bytes. Group size includes its own header; ordinary record payload size does not. Maintain a bounded stack of group end offsets. Every child must fit exactly within its parent, nested groups must close exactly, and the final top-level cursor must equal EOF. Reject sizes smaller than headers, overlapping intervals, truncated headers, unexpected trailers, and arithmetic overflow. Group label/type/stamps and child order remain exact original bytes.

Within each expanded record, subrecords normally have signature[4], size u16, and that many payload bytes. `XXXX` is structural: its own payload must be four bytes containing the extended u32 length for the immediately following real subrecord. Reject dangling/repeated XXXX and an impossible next frame. The next subrecord's u16 length is ignored for reading according to the escape rule; preserve its original header if untouched. Do not count XXXX as a translated field occurrence. For rewritten fields, emit ordinary size when representable, or `XXXX(size=4, extendedSize)` followed by real signature with zero u16 size; retaining an existing XXXX for a shortened edited field is also legal but the serializer must choose one documented deterministic policy. Choose canonical ordinary size for edited values <=65535, XXXX otherwise. Include all header deltas when recomputing enclosing sizes.

A compressed record payload begins with expected expanded length u32 followed by exactly one zlib stream. Inflate in Bend, supporting stored, fixed-Huffman, and dynamic-Huffman DEFLATE blocks. Validate header/check bits, method/window, unsupported preset-dictionary flag, Huffman construction and code-length repeats, end-of-block symbol, reserved symbols, distance <= produced bytes and window, overlapping LZ copies, final block, Adler-32, exact expanded size, and absence of trailing stream bytes. Reject before allocating from a claimed length that exceeds budgets. Bound processing work and cumulative expansion, not just compressed file size.

For unmodified records copy the **original compressed bytes**, even if inspected. For modified compressed records, the first compressor emits a valid zlib stream composed of stored DEFLATE blocks of at most 65535 bytes plus Adler-32. This deliberately sacrifices compression ratio to keep the production algorithm in Bend and reduce compressor complexity. Preserve the compression flag, recompute payload size including the four-byte expansion-length prefix, and account for possibly large output growth before publication. A later deterministic fixed/dynamic compressor is an optimization behind the same interface. Do not call stored-block output compression-equivalent in size, or claim original binary equality for a modified compressed record.

Generic framing is validated throughout the file, including unknown records. Semantic decoding is limited to whitelisted fields. Recognize the deleted-record flag and exclude deleted records from targets. Duplicate record identities that would make a target ambiguous block planning. Do not rewrite TES4 HEDR record counts because records/groups are neither added nor removed. Verify they remain unchanged rather than guessing a new counting convention.

### Whole-file relocation safety

Before permitting any plugin-byte change, scan **all** records/subrecords, not only translated records, against a versioned relocation-safety catalog. The catalog distinguishes audited position-independent fields, supported structural lengths, known offset/layout-dependent metadata, and unclassified forms. Explicit blockers include TES4/OFST, WRLD/OFST, WRLD/CLSZ, OFST or CLSZ in an unaudited context, and the TES4 Optimized File flag unless its exact layout has an audited handler. An unchanged WRLD record can still contain offsets to later records that moved because an unrelated earlier translation grew.

The initial profile has **no offset-metadata rewriter**. If any known offset/layout hazard or unclassified record/field relevant to relocation is present, allow only a plugin-byte-identical operation. Reject every nonidentical plugin rewrite in that case, including equal-length string edits and equal-total-file-size changes; this deliberately stronger rule avoids relying on incomplete knowledge of offset bases, cached sizes, checksums or internal boundaries. A true no-op copies the original bytes and remains possible; localized output with byte-identical plugin must still satisfy its separate table rules. Unknown forms are conservatively unclassified until reviewed as position-independent; adding a translation field alone does not classify the rest of that record or file as safe.

For files whose entire present layout is covered by the audited position-independent catalog, ordinary changes are permitted under the existing minimal-diff rules. A later profile can lift a particular hazard only with a complete specification and fixture-tested proof that every referenced absolute/relative boundary, size and offset remains valid or is correctly updated. Equal output length, unchanged hazard bytes, or unchanged record start alone is not such proof: two records can move internally while the final length stays constant. Never strip OFST/CLSZ, clear an optimized flag, or silently invoke a repair tool to bypass this gate. Include the scan result, catalog version and exact blocker locations in the plan and repeat the gate in provenance verification.

## 6. XML dialect, identity, and matching

Support an explicitly named dialect, `xtranslator-v2`, not all XML ever exported by a translation tool. Root spelling is `SSTXMLRessources`. Require one Params with Version=2 and one Content. Read Addon, source language, destination language, and String children. Each selected entry has List, EDID, REC, Source, Dest, and optional Partial, sID, REC/@id, REC/@idMax. Recognized FuzInfo is nonmatching metadata and is skipped with bounded parsing; it does not authorize file reads. Unknown elements/attributes get a strict unsupported-dialect diagnostic rather than being silently reinterpreted.

Implement a real XML 1.0 subset parser in Bend. Accept UTF-8 with or without BOM, correct declarations, single/double-quoted attributes, self-closing elements, comments, CDATA, XML whitespace, predefined entities, and decimal/hex character references. Reject malformed nesting, duplicate attributes/elements where uniqueness is required, invalid UTF-8/scalars/XML characters, unterminated constructs, raw unescaped `<`/`&`, DTDs, entity declarations, external entities, XInclude, and namespaces outside the supported dialect. No network or filesystem entity resolution. Reject other declared encodings and UTF-16 in v1 rather than misdecoding. Apply XML's own line-ending handling; distinguish missing, empty, and whitespace-only Source/Dest. Preserve translation whitespace and Unicode scalar values; do not trim, case-fold, Unicode-normalize, or decode entities twice.

Observed source semantics: List 0=STRINGS, 1=DLSTRINGS, 2=ILSTRINGS. Exported sID is hexadecimal (minimum width six, not fixed six) and must be parsed as hex even if digits-only. REC text is exactly `RECORD:FIELD`, two case-sensitive four-byte signatures. REC/@id and idMax are decimal; indexes are zero-based and idMax is the highest occurrence index, not count. If both are absent, a single eligible occurrence is required. Require both for repeated-field selection; bounds and computed idMax must agree. Missing idMax in a repeated case is not permission to take the first match.

Recognize EDID forms separately:

1. Literal editor ID: compare to actual EDID of the same record signature, case-sensitively and exactly, and require unique target. Invalid/non-ASCII editor IDs need a later explicitly tested codec profile; do not transliterate them.
2. Exact bracketed `[XXXXXXXX]` fallback from xTranslator: match the complete on-disk raw 32-bit FormID only, and only records without a nonempty EDID. Do not drop the high byte, resolve it as a runtime FE load-order ID, or assume it is safe across master-list changes. A literal real EDID with bracket syntax is an ambiguity error, not guessed away.
3. Cache/hash tuples such as `XXXXXXXX|XXXXXXXX|index|max`, and VMAD property-derived pseudo-EDIDs: recognized as unsupported in this profile. Do not reverse a hash, match hash collisions, or treat them as ordinary FormIDs. Support requires separate producer fixtures and an explicit adapter or a verified mapping manifest.

Candidate lookup is keyed by record signature plus identity, then field signature and **profile-defined exported occurrence**. Validate List against the field's table kind even on inline plugins. On localized plugins, any sID present must equal the current field ID. Every supplied independent identity component must agree; never silently fall back to a weaker key after a disagreement. sID-only string-table exports and Source/Dest-only dictionaries are unsupported for automatic plugin imports in v1 because they do not select a unique record field. An explicit future table-only command can have a different, table-ID-scoped contract.

Source validation and destination comparison are separate operations. For inline plugins the source candidate and current output value are the same field. For localized plugins the source candidate is the **source-language table** value, whereas the current output value is the **destination-baseline table** value for the same original ID and table kind. Default source comparison is exact Unicode text after both sides' CRLF/CR/LF line endings are canonicalized to LF, because XML itself normalizes literal line endings. Report when that EOL-only equivalence was needed. No other whitespace/normalization/fuzzy fallback. Option `--source-eol exact` can be stricter. Destination EOL policy is explicit: preserve the current output value's uniform EOL style; if it has no newline, use the profile default CRLF; reject a mixed-style current value unless `--dest-eol lf|crlf` is explicit. Numeric character references representing literal CR participate in that recorded policy. Encode Dest using the chosen destination codec/EOL policy, then compare that concrete encoded value with the current output value; source EOL equivalence alone does not establish a byte-identical no-op.

For each selected entry first require exactly one location, correct occurrence/cardinality, all identity guards, and a valid encodable destination. Then apply these explicit rules:

- Inline: if current text passes the Source guard, compare its bytes with encoded Dest; identical bytes are unchanged, otherwise schedule a replacement. If Source does not match but current bytes already equal encoded Dest, allow an **already-applied no-write result** after all other guards pass. This is an explicit idempotence exception to the source-match requirement, not permission to write on a mismatch, and means only that the desired value is present, not that this tool previously wrote it. If neither comparison succeeds, fail with source-mismatched.
- Localized: XML Source must match the source-table value even when the destination baseline already contains Dest. On source mismatch fail. Once source validation passes, compare encoded Dest against the destination-baseline value; equal means unchanged/already-applied with no ID allocation, unequal means allocate a fresh ID and patch the selected slot. If XML Source=Dest but the destination baseline differs, this is a change. If source, destination baseline, and Dest are all different but XML Source matches the source table, it is also a legitimate change.

If two entries resolve to one location, identical source/destination/selection metadata may coalesce with both entry numbers recorded; conflicting intents fail. Different target fields with equal source text stay independent. Absent, ambiguous, stale, or unsupported matches block the whole apply except for the explicit inline no-write case above. No auto-rebasing across plugin versions or renumbered masters.

Addon is a consistency guard, not a path. Require its basename to equal the input plugin name using the documented ASCII case-insensitive filename comparison; reject path separators, traversal, or an inconsistent name. A deliberate XML-addon alias needs an explicit CLI value recorded in the plan and does not weaken per-field identity/source checks. Source/destination language arguments must agree with Params or an explicit, recorded alias mapping for the tested xTranslator language codes.

## 7. FO4 field support and encodings

The first published profile is an explicit pair allowlist, not `FULL in every record`. Candidate initial pairs, to be enabled only after binary and xTranslator-export fixtures pass:

- WEAP: FULL; ARMO: FULL; MISC: FULL.
- BOOK: FULL, DESC, CNAM.
- NPC_: FULL, SHRT.
- MESG: FULL, DESC, NNAM, ITXT.
- INFO: NAM1, RNAM.
- QUST: FULL, CNAM, NNAM.
- TERM: FULL, NAM0, WNAM, BTXT, ITXT, RNAM, UNAM.
- GMST: DATA only when an actual EDID begins with lowercase `s` and the record satisfies the tested GMST layout.

Use xTranslator's FO4 List mapping: DESC and BOOK/QUST CNAM use DLSTRINGS except a specific audited override; INFO NAM1 uses ILSTRINGS; the other listed fields use STRINGS. Conditional layouts must include sequence context, not just signature. Repeated occurrences in INFO, QUST, TERM, and object templates must match xTranslator export indexing on the exact accepted layouts. If that cannot be proven by fixtures for a record variant, that variant is unsupported even if another form of the same record works.

PERK EPFD/EPF2, RACE complex names, INNR, arbitrary FULL/DESC/ATTX fallbacks, embedded VMAD strings, PEX, MCM, interface files, and TES4 author/description are explicitly outside this first allowlist. PERK is especially dangerous: the same EPFD signature can mean floats, FormIDs, an inline string, or a localized string depending on context. Add these through independent profile work with fixture coverage, never raw search-and-replace.

For inline accepted fields require the exact NUL-terminated form specified by the profile: trailing NUL present, no embedded NUL, and no unexplained suffix bytes. Serialize the destination as strict encoded bytes plus one terminator. Check byte length, not character count, before choosing short/XXXX size. Physical resource limits are not a guarantee that all UI text will fit; report advisory display-length risks separately.

Require an explicit inline plugin encoding, initially UTF-8 or Windows-1252. Reject malformed input and unmappable destination scalars; never substitute `?`, strip bytes, or guess encoding from successful decoding. Inline input and output must use the same declared encoding. Cross-encoding only the edited fields would produce a mixed-encoding plugin, so v1 rejects that operation. An English ASCII source can validly be declared UTF-8, but a CP1252 mod needing Japanese output needs a future whole-plugin transcoder with complete field coverage or prior verified conversion. Disclose this constraint in capabilities and planning, not after writing.

Localized table input and output encodings may differ because the entire table can be parsed and consistently serialized. Each provided table's encoding is explicit, not inferred from the language suffix. UTF-8 is the intended target for Japanese; font/glyph support in the game is a separate user-side concern.

Text placeholder validation is a separate policy. Only add token grammars verified against FO4 fixtures; preserve protected aliases/control tokens exactly and detect missing/changed tokens. Unrecognized markup is flagged for review, not rewritten. The tool cannot prove linguistic correctness or that a translation preserves every script/UI convention. The binary safety verifier must not be described as a translation-quality guarantee.

## 8. Localized workflow: record-scoped single-language bundles

Never replace a four-byte localized ID with encoded text or toggle the TES4 localized flag. The core record matcher still selects concrete fields, resolves their table kind and nonzero ID, and loads XML Source from the explicit source-language table. Missing table/ID, wrong kind, zero ID, invalid table, or contradictory XML sID is a hard error. No fallback from STRINGS to another kind just because a matching number exists.

Parse each loose table as count u32, data-size u32, `count` entries of ID u32 and data-relative offset u32, then the declared data block. Apply section 4's preallocation and cumulative budgets before reading directory entries into an index. Check multiplication/addition, exact file length, unique IDs, valid offsets, and each referenced string's complete bounds. STRINGS is NUL-terminated; DLSTRINGS/ILSTRINGS begin with u32 byte length including the final NUL. Length must be >=1 and fit the data block. Reject interior NULs or missing terminators for the accepted profile. Multiple IDs may share an offset; preserve semantic aliasing without assuming directory order equals data order. Unreferenced data bytes are allowed and preserved where possible, not treated as a license to skip bounds checks. Preserve entries not mentioned by XML, including orphan table IDs.

Defend against alias/overlap amplification explicitly. Sort the bounded directory metadata by offset and process distinct offsets in order. Validate and decode each identical table-kind/offset/length/codec span once; directory entries refer to that validated span rather than copying its text. For STRINGS, find the terminator with a bounded scan once per unique offset. If a later distinct offset falls inside an already validated span, reject it as an unsupported overlapping-tail layout **before** rescanning or decoding it. Apply the same interval rule to DL/IL spans including their four-byte length prefix. Exact identical-span aliases are supported; partially overlapping or nested spans are rejected in v1 even if another tool accepts them. This yields bounded directory sorting plus a bounded data scan rather than entry-count times tail-length work. Logical referenced-byte and output budgets still apply to exact aliases; memoization is not permission to materialize the same megabyte millions of times. Output serialization reuses original-baseline aliases when the encoded values are identical, while keeping newly allocated per-slot IDs distinct. Precompute serialized directory/data sizes before output allocation or writes.

Provide a destination baseline: existing target tables, or an explicit choice to use source text for every untranslated entry. When using existing target tables require at least the complete source ID set for each corresponding kind, retain target-only entries, and reject unresolved IDs used by supported fields. This avoids creating a translation-only table that silently deletes thousands of untouched strings. All table kinds that exist in source are included in the bundle. If a kind is absent, it may be omitted only if the accepted plugin profile proves no field references that kind; otherwise request it. Source and target language table filenames must be generated by a tested FO4 locale-code mapping (e.g. en/ja), not guessed from English language names or taken from arbitrary XML paths.

Shared IDs are the principal semantic hazard. **Do not edit an existing ID's value in place** for a record-scoped import. For every actually changed target slot, allocate a fresh nonzero u32 ID, append a destination value under that ID, and patch only that slot's four-byte ID. Existing IDs and their destination-baseline values remain unchanged, so unselected fields sharing the old ID retain their baseline values. Allocate one new ID per target slot in stable original record/subrecord order; do not deduplicate to save a few bytes in v1. This also permits two formerly aliased fields to receive different translations safely.

Reserve IDs already present in every supplied table. To avoid making an unrecognized pre-existing reference suddenly resolve, also conservatively reserve every u32 value appearing as any four-consecutive-byte little-endian window in every decompressed record payload, including unknown subrecords. The reference format is a literal u32 in this supported format family; hidden alternate encodings are outside that contract. Scan with a rolling four-byte window, not per-window allocations. Allocation can mark a fixed-size bitmap for a candidate interval (initially IDs 1..1048575), choose the lowest free IDs, and expand/re-scan bounded intervals when necessary. Report allocation exhaustion/resource budget failure; never wrap to zero or collide. Reserve chosen IDs immediately. This conservative scan is intentionally broader than recognized string fields and must be benchmarked before release.

New IDs are added only to the requested target-language tables. Therefore the published artifact is explicitly a **single-language replacement bundle**: modified plugin plus complete target-language tables under `Strings/`. Manifest and CLI state that the output plugin is not safe to pair with arbitrary old tables in other languages because its new IDs would be missing. To support several languages later, require complete baselines for each and add each new ID to every language, using that language's old-ID value for unchanged languages. Never imply source tables remain valid with the new plugin.

Files remain named for the original plugin stem. Do not copy BA2/BSA, voice files, meshes, or scripts. The bundle depends on the original mod's other assets and should be installed as a replacement/override in a mod manager after testing, not as a self-contained new mod. The program does not install or activate it.

No-op localized entries, determined against the destination baseline only after source-table validation, do not allocate IDs. A repeated import against already rewritten output with the old XML may have mismatching old sIDs; reject rather than weakening matching. A later provenance-aware idempotence option would require the original inputs and a recomputed prior plan, or a separately trusted provenance record, to verify the original-to-new slot mapping. A self-consistent editable manifest and its hashes alone do not establish that provenance. Inline idempotence and localized provenance-dependent reapply must not be conflated.

## 9. Writer, verification, and publication

Planning is pure with respect to external state. Construct an ordered set of nonoverlapping patches; reject overlap. Each patch contains original record/field identity, old byte/value digest, encoded replacement, old/new sizes, table kind and IDs where relevant, and XML provenance. Precompute all new record/group/file sizes with checked arithmetic before output begins, including actual compressed rewrite sizes. Apply the whole-file relocation-safety gate before approving any nonidentical plugin output; a zero net size delta is not an exemption. Apply all table/output/working-memory budgets before allocation and publication.

The writer preserves raw untouched subrecords and entire untouched records/groups wherever possible. For a changed record, retain original subrecord order and all unrelated bytes, rebuild only targeted subrecords and necessary XXXX framing, and then recompress only if originally compressed. Recompute group sizes bottom-up from actual emitted children, not a character-count approximation. Do not alter any non-size record header bits, FormID, revision, form-version, master order, TES4 text, or record count.

Write inside an exclusively created private **staging parent** on the final output's filesystem, never into the input path. Keep an open directory descriptor for this private parent, and create the publishable bundle as its child with a fixed internal name such as `publish`. Keep both the private-parent and bundle descriptors open through verification and publication. The directory renamed at publication is therefore a child of a held private directory, not a public-parent entry that an unrelated writer could substitute. Private staging parents and their children have mode 0700 and no effective write ACL grants to other principals; files have mode 0600 until any explicitly documented publication-permission step. Source snapshots are outside `publish`, so they are never accidentally included in the bundle.

Required OS effects are a tiny audited filesystem substrate: directory-handle-based exclusive creation, ownership/mode/ACL inspection, no-follow regular-file opening, short-write handling, fsync+checked close, directory fsync, and atomic **no-replace** rename. These are storage primitives, not external parsers or writers. On initial Linux target publish with a tested primitive such as `renameat2(privateStagingParentFd, "publish", outputParentFd, finalName, RENAME_NOREPLACE)`; do not check-then-rename. `RENAME_NOREPLACE` protects the destination only; it does not itself prove that the source pathname still denotes the verified directory. The private held source parent and namespace trust policy below supply that guarantee. A last-moment inode comparison or rehash alone does not close a source-name substitution race. Keep all production format logic in Bend. If “only Bend source, with no extra runtime primitive” is required, offer a clearly labeled verified staging-only mode and do not claim atomic publication; do not silently put publication logic in a shell converter.

Reject output path aliases, existing destinations, unsafe generated filenames, and nonregular inputs where relevant. Anchor output operations to an opened parent directory and use exclusive file creation/no-follow flags. XML never supplies an output path. The CLI has no overwrite/in-place option in v1. Non-atomic/network filesystems unsupported by the publication contract cause an error, not a quiet fallback. A final-directory existence check is advisory only; the no-replace operation is authoritative under races.

Namespace trust is an explicit initial-platform requirement. The output parent and its traversed ancestors must be owned by the invoking account or trusted system root, and must not grant effective namespace-modification rights to another principal through group/other mode bits or access ACLs. Conservatively reject writable shared/sticky directories in v1 rather than claiming a subtle exception is safe. Inspect both access and inherited/default ACL behavior and recheck the actually created private staging parent; if the platform cannot establish those rights, refuse transactional apply. Open and walk directories with no-follow, directory-relative operations; later effects use retained descriptors rather than resolving textual ancestors again. Permission checks establish the stated trust boundary; they are not a defense against a trusted owner subsequently acting maliciously.

The protected threat model includes unrelated unprivileged accounts attempting path/symlink substitution, not malicious processes with the invoking account's credentials or administrative rights. The user must not concurrently rename/chmod/edit the work/output namespace. Do not claim isolation from another same-account process that can change directory permissions or inspect the process. After publication, the destination owner can legitimately modify or delete the output; atomic verified publication attests only to the bundle at the publication boundary, not permanent tamper resistance. Later integrity checks detect changes only relative to their stated trust level.

Cleanup operates only through held descriptors inside the privately owned work area, using the recorded set of created entries and no-follow traversal. Never recursively remove a path reached by re-resolving the public stage name, a substituted symlink/directory, or an existing final destination. On unexpected identity/type/entry changes, stop cleanup and report a residual work area rather than trying to reclaim it aggressively. After successful publication the bundle is no longer a cleanup target. After an uncertain rename outcome, establish whether publication occurred before cleaning any source artifacts; do not infer that a missing source means an arbitrary final directory belongs to this run. Removing the now-empty private staging-parent entry is permitted only within the established trusted namespace and with its recorded identity confirmed; if that trust or identity is uncertain, leave it alone. Identity checks aid diagnosis/cleanup but never substitute for the namespace protection needed at rename time.

After all writes, reopen staged artifacts and verify:

1. Every artifact passes framing, compression/checksum, encoding, and table validation with exact EOF.
2. Every planned slot contains exactly its planned destination (or new localized ID with the correct table value).
3. Structural identity, record/group order, FormIDs, flags, masters, and counts are unchanged; the whole-file relocation-safety scan passes for the actual changes, including offset metadata outside targeted records.
4. Every unmodified record is byte-identical, including its compressed representation. Within changed records, every non-target logical subrecord is byte-identical after decompression. Only intended strings, local framing lengths, compression envelope, and ancestor sizes may differ.
5. For localized output every old table ID retains the destination baseline value, all planned new IDs are unique and resolve in the correct kind, and no unselected field ID changed. Record/table namespaces never get merged.
6. Output sizes match actual serialized bytes; all digests and report counts reconcile.

The mandatory prepublication verification is a **full provenance audit** against the original snapshots and recomputed in-memory plan, not merely successfully reparsing the writer's output. Reuse framing primitives but keep an independently traversed invariant checker and independent external test oracles, since a parser/writer can share the same bug.

Write manifest/report inside staging, including source/XML/table hashes, output hashes, compiler/tool/profile versions, options, field changes, exclusions, and single-language limitations. Hash raw input/output bytes; use a separate canonical plan encoding for the plan digest. Avoid absolute paths and full source/translated text in reports by default; `--include-text` is explicit. Reports must escape JSON, terminal control characters, and non-UTF-8 path bytes safely.

Manifest trust boundary: a manifest is untrusted metadata, not an authorization token or cryptographic attestation. Integrity-only `verify --bundle` checks the allowed schema/version, artifact names and types, supported parse profiles, output digests, sizes and internal counts against the supplied artifacts. It opens only allowed relative regular-file paths inside the bundle, with no traversal or symlink escape, and never follows a manifest path to fetch an original input or run code. A maliciously edited bundle plus matching edited manifest can pass integrity-only verification; the result must say that original-change provenance was not checked.

For later full `verify --provenance`, independently specified original input paths and import options are authoritative. Snapshot them anew, validate their hashes against the manifest as a consistency check, recompute identities, source guards, destination comparisons, allocation, and the plan under the supported pinned profile/tool semantics, then run all six original-to-output checks above and compare deterministic output bytes. Reject mismatched options, altered plan claims, missing originals, unsupported historical semantics, or an inconsistent manifest. Original source tables and **original target baseline** tables are required; the bundle's newly written tables cannot replace those inputs. A hash previously saved outside the bundle can provide an additional trusted anchor only when its trust is explicit; it does not reconstruct missing originals or turn an integrity-only check into a full audit. A valid recomputation demonstrates the declared transform relative to the supplied originals, not who authored or approved those originals.

Flush/fsync and check-close every artifact file, then fsync **every created directory bottom-up**, including `Strings/` and any other nested artifact directories, the publishable bundle root, and its private staging parent. Only after all those operations succeed may the verified child be atomically moved from the held private parent to the held output parent. Then fsync both source staging parent and destination output parent to persist the cross-directory rename. Fsyncing the bundle root alone does not make nested directory entries durable. This gives bundle-level atomic visibility on the supported filesystem; it does not mean separately renaming three tables and a plugin is atomic. Failure before publish leaves only a marked private stage. Failure after a successful rename but before required parent fsyncs is an uncertain durability outcome: report the visible output path and verify state before any retry; never blindly overwrite. Original inputs remain untouched throughout. Do not describe any software as proof against hardware failure or all filesystem crashes.

## 10. Test plan and acceptance gates

Unit vectors in Bend cover endian arithmetic boundaries, UTF-8 overlong/surrogate/out-of-range failures, CP1252 round trips/unmappable characters, XML entities/CDATA/whitespace/declarations/BOM, SHA-256 known answers, zlib Adler-32 and all DEFLATE block kinds, and table offset/length bounds. Tests have explicit expected failure codes, not only “does not crash.”

Synthetic plugin fixture matrix:

- ESP, ESM, ESL extension and TES4-flag combinations; do not infer flag from extension.
- Nested/empty groups; unusual preserved stamp/unknown bytes; malformed parent boundaries.
- TES4/OFST, WRLD/OFST, WRLD/CLSZ and unclassified relocation hazards outside translated records: earlier growth, shrinkage, two edits with equal final file size but moved interior boundaries, equal-length edits, compressed-record rewrites, and true byte-identical no-ops. Initial policy rejects every nonidentical plugin rewrite with a blocker and preserves all hazard bytes on allowed no-ops; no metadata is stripped. Include unknown-field rejection and explicitly audited position-independent opaque-field acceptance.
- Every enabled record/field pair, exact source text, EOL-only equality, stale source, already-applied text, empty/space-only destinations, forbidden embedded NUL, Japanese and non-BMP scalars.
- Explicit comparison truth tables: inline current=Source, current=Dest with Source different, current matching neither, and repeated application with zero writes; localized Source=Dest with destination baseline different, destination baseline=Dest, all three values different with a valid source guard, and invalid source with destination already equal to Dest. Repeat each localized case with shared original IDs and confirm only changed slots allocate IDs.
- Repeated INFO NAM1, QUST CNAM/NNAM, TERM BTXT/ITXT, and object-template repeated FULL fixtures; missing or off-by-one id/idMax; duplicate literal EDIDs; absent EDID bracket FormIDs; literal bracket-EDID ambiguity; foreign master-order ID mismatch; XML cache tuples and VMAD refused.
- XXXX at 65535/65536-byte boundary including terminator and crossing in both directions; inconsistent/truncated escapes; no wraparound in group/record sizes.
- Changed and unchanged compressed records; stored/fixed/dynamic streams; malformed tables, invalid distances, wrong checksum/expanded size, dictionaries, trailing bytes, expansion bombs, and output growth.
- Localized ID 0, missing ID/table, repeated ID directory error, shared offsets, shared IDs across fields, same numeric ID in different table kinds, different destinations for formerly shared IDs, target-only table entries, source fallback policy, new-ID collision/bitmap expansion, and single-language manifest enforcement.
- Table amplification: one million directory entries sharing a 1 MiB tail, one million entries referencing overlapping suffixes, and smaller variants under the entry cap but over logical-byte/work/output/memory budgets. Above-cap counts fail before count-sized allocation; exact aliases decode once; partial overlaps fail before repeated tail scans. Test UTF-8 expansion during baseline transcoding, aggregate limits across six tables, output-budget preflight, budget exhaustion during verification, and zero publication on every failure.
- IO failures after each write/flush/close/publish step, disk full, destination races, symlink/path alias attempts, process cancellation, stage cleanup, and uncertain post-rename fsync outcomes. Inject nested `Strings/` fsync failure and crash points before/after each bottom-up directory sync and publication; no publication follows a failed prepublication sync.
- Adversarial namespace tests: a parent writer attempts to rename the verified bundle aside and replace its public name with a directory or symlink immediately before publication. Untrusted writable parents/ancestors/ACL grants must be rejected; within the supported private-source-parent setup an unrelated account cannot replace the `publish` child, and retained descriptors must not follow a substituted outer name. Test inherited/default ACLs, denied ACL inspection, unexpected cleanup entries, substituted cleanup targets, and uncertain rename outcomes. Cleanup must never remove the attacker's substitute, an original input, or an already published bundle. Same-account/admin adversaries are explicitly outside the guarantee, not silently counted as passing these security tests.
- Verification trust tests: edited manifest only, edited artifacts plus recomputed malicious manifest, missing originals, mismatched source/target baselines, changed options, unsupported historical profile, external path/symlink claims, and snapshot cleanup/explicit retention. The malicious self-consistent case may pass integrity-only checks but must not receive a provenance result without a successful independent recomputation.

Property/metamorphic tests: no-op output plugin equals input byte-for-byte; unchanged subrecords remain exact; output parse reaches EOF; serialize sizes match actual bytes; patch order independent when targets are distinct; the same inputs/options/compiler produce identical plugin/table bytes; missing/ambiguous/source-mismatched entries never publish; injected corruptions fail; all resource budgets fail closed.

Use independent **test-only** oracles: Python stdlib zlib/XML/struct for randomized interoperability tests; FO4Edit/xEdit to load output, check expected field values and errors; and xTranslator to export before/after fixtures and verify index/status/encoding dialect behavior. Those tools do not perform production import. Synthetic fixtures should be authored by the project; real mod fixtures need redistribution permission. Never bundle Bethesda game masters as test data.

Release acceptance additionally requires a lawful representative real-plugin corpus covering each enabled version, field codec, repeated layout, compression path, and localization mode; a comparison against source/oracle results; negative corpus success; and a manual game smoke test for at least one inline and one localized plugin in the target FO4 version. If xEdit/game validation was not run, the result is a prototype with that verification gap, not “game safe.” Publish measured runtime/RSS and tested maximum sizes. Compiler proofs supplement but do not replace IO/backend/oracle testing.

Candidate Bend laws: cursor never advances outside its enclosing span; checked size operations never wrap; successful plan contains unique nonoverlapping locations; no selected entry is silently dropped; unchanged serializer branches return original bytes; allocated IDs are nonzero and outside the reserved set. Prove only laws actually encoded over the implementation and checked by the pinned toolchain. Do not claim proofs cover the compiler, OS, filesystem, codecs, or game semantics without corresponding proofs.

## 11. Implementation order and honest scope

Gate A: prove the pinned Bend runtime can do the required binary IO and bounded-buffer workloads. Implement and independently test the minimal filesystem effects, ACL-aware namespace checks, held-private-parent publication, and safe cleanup, or select staging-only capability. No format writes before this gate passes.

Gate B: generic read-only framing, byte-preserving no-op copying, strict XML v2 parsing, codecs, SHA-256, and stable diagnostic reports. Validate all malformed-input handling.

Gate B also builds the versioned whole-file relocation-safety catalog. No mutation capability is enabled for a plugin with unclassified relocation-relevant forms or known offset metadata; a copied-byte prototype alone does not pass this gate for rewriting.

Gate C: plan/apply/verify inline uncompressed fixtures for a very small enabled allowlist. Expand to repeated cases and XXXX only after their fixtures pass. This remains an explicitly limited prototype.

Gate D: full bounded inflate, stored-block zlib writer, unchanged compressed-byte preservation, and differential compression tests. Enable compressed imports.

Gate E: complete localized table parsing/baselines, record-scoped clone IDs, conservative reservation scan, target-language bundle output and verification. Until this gate passes, localized plugins fail immediately with an honest unsupported-mode diagnostic; they are not counted as completed product support.

Gate F: transactional bundle publication/fault injection, corpus/oracle/game validation, packaging, compatibility matrix, and release. The full initial product requires A through F. Broadening to all xTranslator fields, cache XML, UTF-16 XML, whole-plugin transcoding, additional languages per bundle, BA2 extraction, or other games is separately tracked, not assumed by the architecture.

## 12. Design-review process

This document is the initial design. At least five fresh independent review rounds are required by the task. Each review records reviewer identity/model, input design revision/hash, findings with concrete failing examples, severity, proposed fix, and disposition. The designer fixes findings and adds a regression requirement before the next fresh review. A later reviewer receives the current design and user requirements, not a prompt to rubber-stamp previous conclusions. If round five still has findings, continue fresh review/fix rounds until one reports no remaining actionable findings within the stated scope. “No findings” is a scoped review outcome, not a guarantee of no bugs. Do not claim those rounds occurred until the actual reports exist.

## Open implementation evidence, not hidden assumptions

- No Bend compiler is installed in the inspected workspace, and this design stage did not compile code.
- Exact accepted FO4 header/form-version tuples require captured fixtures and validation before enabling them. The CLI must list its supported versions instead of accepting all versions.
- Repeated-field index behavior, localized table filename locale mapping, and every enabled contextual field need real xTranslator export fixtures for the pinned producer.
- Publication primitives, filesystem behavior, resource budgets, and conservative ID-scan performance are engineering gates, not existing capabilities.
- Whole-file relocation classification is required in addition to the translation-field allowlist. The first release refuses nonidentical plugin rewrites with OFST/CLSZ or unaudited layout hazards rather than claiming opaque-byte preservation makes them safe.
- A complete initial release still has a field allowlist. It refuses unsupported selected entries and must clearly report that breadth limit rather than imply every Fallout 4 translation XML is supported.
